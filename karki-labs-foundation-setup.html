Stage 1 · the manual foundation

The groundwork before Terraform.

A handful of things must exist by hand before infrastructure-as-code can run — because Terraform itself needs them to start. Here's the shape of it, then the exact steps.

The picture

What lives where

Your organization is the outer container. Inside it you build one bootstrap project by hand (left) — a "control room" holding Terraform's memory and identity. Everything on the right is what Terraform will create for you afterwards.

You build the left side by hand today. Terraform, using the state bucket + identity, then creates the dashed boxes on the right — the two environment projects. That handoff is the whole point of Stage 1.

The setup · run as admin@nepalimaan.com

Complete foundation, step by step

Each block has a copy button. Run them top to bottom. If a step errors, stop and check the note before continuing.

1

Set variables

makes: nothing yet

Just saves your IDs so the later commands stay short and you don't retype them.

export ORG_ID=190096138732
export REGION=australia-southeast1

gcloud billing accounts list        # copy the ACCOUNT_ID where OPEN = True
export BILLING_ID=<paste-it-here>
If billing accounts list is empty: your billing account is owned by your personal Gmail, so the admin can't see it. Fix — Console → Billing → Account management → add admin@nepalimaan.com as a Billing Account Administrator, then re-run.
2

Create the bootstrap project

makes: the control room

The project that will hold Terraform's memory and identity. It is not nonprod or prod — it sits apart so an environment can never delete it.

gcloud projects create karki-labs-bootstrap --organization=$ORG_ID
gcloud config set project karki-labs-bootstrap
gcloud billing projects link karki-labs-bootstrap --billing-account=$BILLING_ID

# turn on the APIs the control room itself needs
gcloud services enable \
  cloudresourcemanager.googleapis.com cloudbilling.googleapis.com \
  iam.googleapis.com iamcredentials.googleapis.com \
  serviceusage.googleapis.com storage.googleapis.com
If karki-labs-bootstrap is taken (project IDs are globally unique), add digits — e.g. karki-labs-bootstrap-7321 — and use that name everywhere below.
3

Create the state bucket

makes: Terraform's memory

A versioned bucket where Terraform records what it built. Versioning means you can recover a previous state if something goes wrong.

gcloud storage buckets create gs://karki-labs-tf-state \
  --project=karki-labs-bootstrap --location=$REGION --uniform-bucket-level-access
gcloud storage buckets update gs://karki-labs-tf-state --versioning
4

Create Terraform's identity + grant access

makes: the terraform-sa account

A service account is a non-human login that Terraform uses. The roles let it create projects and folders, and build networking, GKE, DNS, and registries inside them.

gcloud iam service-accounts create terraform-sa \
  --project=karki-labs-bootstrap --display-name="Terraform"

export TF_SA="terraform-sa@karki-labs-bootstrap.iam.gserviceaccount.com"

# org-level roles: create + build the environments
for ROLE in \
  roles/resourcemanager.projectCreator \
  roles/resourcemanager.folderAdmin \
  roles/resourcemanager.projectIamAdmin \
  roles/serviceusage.serviceUsageAdmin \
  roles/compute.networkAdmin \
  roles/container.admin \
  roles/dns.admin \
  roles/artifactregistry.admin \
  roles/iam.serviceAccountAdmin \
  roles/storage.admin; do
  gcloud organizations add-iam-policy-binding $ORG_ID \
    --member="serviceAccount:$TF_SA" --role="$ROLE" --condition=None
done

# let it attach billing to projects it creates
gcloud billing accounts add-iam-policy-binding $BILLING_ID \
  --member="serviceAccount:$TF_SA" --role="roles/billing.user"
These roles are deliberately broad so you don't hit permission walls while learning. Narrowing them to least-privilege is a later hardening exercise — not now.
5

Set up impersonation (no key file)

makes: safe access, no secret

Instead of downloading a secret key file (which can leak), you let your admin account borrow the SA's identity on demand. Nothing to store, nothing to lose.

# allow YOU to act as the Terraform SA
gcloud iam service-accounts add-iam-policy-binding $TF_SA \
  --member="user:admin@nepalimaan.com" \
  --role="roles/iam.serviceAccountTokenCreator"

# the credentials Terraform will read (sign in as admin@nepalimaan.com)
gcloud auth application-default login
6

Create the folders

makes: nonprod + prod shelves

The two shelves inside your org where the environment projects will live. Terraform will place each project into its folder.

gcloud resource-manager folders create --display-name="nonprod" --organization=$ORG_ID
gcloud resource-manager folders create --display-name="prod"    --organization=$ORG_ID
gcloud resource-manager folders list --organization=$ORG_ID     # note both FOLDER IDs
Write down the two folder IDs it prints — Terraform needs them to know which shelf each project goes on.
7

Verify the whole foundation

makes: confidence

Five quick checks. When all pass — especially "impersonation OK" — the manual groundwork is complete and Terraform can take over.

gcloud projects describe karki-labs-bootstrap --format="value(parent.id)"   # = 190096138732
gcloud storage ls                                                # shows the tf-state bucket
gcloud iam service-accounts list --project=karki-labs-bootstrap  # shows terraform-sa
gcloud resource-manager folders list --organization=$ORG_ID      # shows nonprod + prod
gcloud auth print-access-token --impersonate-service-account=$TF_SA >/dev/null && echo "impersonation OK"

The handoff

Where Terraform picks up

Your first Terraform will point at the state bucket, act as terraform-sa via impersonation, and its very first job is to create the two environment projects. The top of that config looks like this:

terraform {
  backend "gcs" {
    bucket = "karki-labs-tf-state"
    prefix = "bootstrap/terraform.tfstate"
  }
}

provider "google" {
  impersonate_service_account = "terraform-sa@karki-labs-bootstrap.iam.gserviceaccount.com"
  region                      = "australia-southeast1"
}

That's the foundation.

The left side of the diagram — built by hand, once. From here on, everything is code: Terraform reads the state bucket, borrows the terraform-sa identity, and creates karki-labs-nonprod and karki-labs-prod inside their folders.

Run Parts 1–7, get "impersonation OK", and you're ready to write your first real infrastructure.
